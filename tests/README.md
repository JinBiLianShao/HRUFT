# 测试说明与实测数据

作者：连思鑫

这份文档记录 HRUFT Pro 的测试怎么跑、测了什么、以及在开发机上的实测数据。
数字只是**我这台机器**的结果，换机器绝对值会变，重点看相对关系。

---

## 一、怎么跑

```bash
# 先构建
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j

# 跑全部测试（约 2 分钟，不含 512MB 大文件）
./tests/run_all.sh

# 指定二进制
HRUFT_BIN=/path/to/hruft ./tests/run_all.sh

# 单独跑某一套
HRUFT_BIN=./build/hruft bash tests/functional/test_transfer.sh
HRUFT_BIN=./build/hruft bash tests/security/test_malicious.sh
HRUFT_BIN=./build/hruft bash tests/robustness/test_protocol.sh
```

性能基准单独跑，因为耗时长且数值随机器波动大：

```bash
# 默认 256MB × 3 轮
HRUFT_BIN=./build/hruft ./tests/performance/bench.sh

# 自定义
BENCH_SIZE=536870912 BENCH_ROUNDS=5 BENCH_DIR=/data/bench ./tests/performance/bench.sh
```

## 二、测试套件

### 1. 功能测试 `tests/functional/test_transfer.sh`

验证传输正确性，每个用例都**比对 md5**，不看日志说什么，只看落地文件对不对。

| 编号 | 用例 | 为什么要有它 |
|------|------|--------------|
| 1 | 空文件 | 0 字节时收发循环的边界最容易写错 |
| 2 | 1 字节 / 1KB | 极小文件不该走特殊路径 |
| 3 | 4MB±1 / 8MB±1 | 4MB 是应用层分块大小，边界差一字节暴露循环 bug |
| 4 | 32MB | 多次分块 |
| 5 | 512MB | 覆盖多秒传输、进度刷新、计数增长 |
| 6 | 中文 + 空格文件名 | Windows 下曾有 wstring 窄化问题 |
| 7 | savepath 是裸文件名 | 旧版这里直接崩（`create_directories("")`） |
| 8 | savepath 是已存在目录 | 应自动落到目录内 |
| 9 | 同名文件不覆盖 | 旧版用秒级时间戳，同秒传两次会覆盖 |
| 10 | 连续传输 | 确认没有跨连接的状态残留 |
| 11 | `--detailed` | 统计模式不该影响传输结果 |
| 12 | `--no-cc` | 自定义拥塞控制路径能跑通 |
| 13 | MSS 边界 536 / 8900 | 上下限都要能工作 |
| 14 | window 128MB | 大窗口路径 |
| 15 | 两端 MSS 一致性 | **性能回归守卫**，见下方说明 |
| 16 | 默认参数基线 | 记录数字，便于对比 |

### 2. 安全测试 `tests/security/test_malicious.sh`

文件名完全来自网络，是最容易出事的地方。这套测试会**自己编译一个伪造对端**，
发任意文件名的协议头，然后检查接收端有没有被写到预期目录之外。

| 攻击 | 预期 |
|------|------|
| `../../evil.sh` | 降级为 `evil.sh` |
| `../../../../tmp/evil.sh` | 降级为 `evil.sh` |
| `/etc/passwd` | 降级为 `passwd` |
| `/tmp/evil.sh` | 降级为 `evil.sh` |
| `..\..\evil.sh` | 降级为 `evil.sh` |
| `..` / `.` | 直接拒绝 |
| 文件名含 NUL | 拒绝（否则会被静默截断） |
| 文件名非法 UTF-8 | 拒绝 |
| 谎报 16EB 大小 | 不预分配、不挂死 |

另外还测参数校验：端口 0 / 70000 / 负数 / 非数字、MSS 越界、窗口过小、未知选项。

### 3. 健壮性测试 `tests/robustness/test_protocol.sh`

用手工构造的畸形帧打接收端。判定标准是：**要么明确报错退出，要么正常结束，
绝不允许崩溃、挂死或残留临时文件**。

覆盖 26 种畸形输入，包括：magic 错、版本错、帧长 0/1/最大/超 64MB、
payload 截断、未知帧类型、文件名长度 0/不匹配/超限/恰好 65536、
谎报 16EB、数据不足、哈希长度不对、跳过哈希、帧类型错位、
中途断开、连上就断、100 个重复协议头、单字节慢速发送。

> 这套测试抓到过一个真 bug：异常路径下 `.part` 临时文件会残留。
> 修法是加 `TempFileGuard`（RAII），任何异常退出都会自动清理。

### 4. 性能基准 `tests/performance/bench.sh`

只测量、不判定。每档跑 N 轮取中位数，**每轮都校验大小和哈希，校验不过的那轮直接丢弃**——
否则「传失败了所以很快」会被误当成好成绩。

### 5. 丢包环境 `tests/robustness/test_packet_loss.sh`

loopback 不丢包，很多问题测不出来。这个套件用 `unshare` 建网络命名空间，
再用 `tc netem` 注入 1% / 2% / 5% 丢包，在里面验证：

- 三种模式（默认 / `--fast-start` / `--no-cc`）在各丢包率下内容是否完整
- `--fast-start` 是否显著快于默认（要求至少 2 倍，实测 12.9 倍）

环境不满足（没有 unshare / tc / netem 模块）时明确 **SKIP**，不会假装通过。

## 三、实测数据

### 环境

| 项 | 值 |
|----|-----|
| CPU | 8 核 |
| 内存 | 31 GB |
| 磁盘 | NVMe / btrfs（`/home`），测试目录放在这里 |
| 网络 | loopback（127.0.0.1），**不是真实网络** |
| 编译器 | GCC 16.2.1，`-O2` |
| 文件 | 512 MB 随机数据 |

> **重要**：loopback 测不出真实网络特性（延迟、丢包、带宽上限）。
> 下面的数字只反映「本机协议栈 + 磁盘」的天花板。

### 纯 UDT 天花板（不读盘、不写盘、不算哈希）

单独写了个最小程序，只做 `UDT::send` / `UDT::recv`，用来确定瓶颈在哪：

| MSS | window | 吞吐 |
|-----|--------|------|
| 1500 | 10 MB | 391 MB/s |
| 8900 | 10 MB | 571 MB/s |
| 8900 | 128 MB | **1081 MB/s** |

结论：UDT 本身能跑 1 GB/s 以上，完整程序只有 300~600 MB/s，
**差的那部分是我的代码**，不是协议栈。

### 各环节单独耗时（512 MB）

| 环节 | 耗时 | 等效吞吐 |
|------|------|----------|
| BLAKE3 计算 | 0.066 s | 7741 MB/s |
| 单次 memcpy | 0.022 s | 22841 MB/s |
| 顺序写盘 | 0.119 s | 4301 MB/s |
| 顺序读盘 | 0.067 s | 7603 MB/s |

哈希和磁盘加起来约 0.25 s，但实际传输要 0.9~1.7 s，
说明时间主要花在 UDT 的逐包处理上——**包数是关键变量**。

### MSS 的影响（512 MB，window 128 MB）

| MSS | 包数 | 吞吐 |
|-----|------|------|
| 1500 | 368773 | 378 MB/s |
| 3000 | 181637 | 518 MB/s |
| 4500 | 120581 | 502 MB/s |
| 6000 | 90245 | 545 MB/s |
| 8900 | 60677 | **618 MB/s** |

包数降到 1/6，吞吐提升约 63%。这是**单项影响最大的参数**。

> MSS 上限 8900 是 UDT 的限制，实测 12000 / 16000 / 32768 / 65535 全部传输失败。

### 流水线深度的影响（512 MB，MSS 8900，window 128 MB，5 轮中位数）

| 深度 | 在途数据 | 吞吐 |
|------|----------|------|
| 4 | 16 MB | 564 MB/s |
| 8 | 32 MB | 569 MB/s |
| 16 | 64 MB | 561 MB/s |

**基本无差异**，所以保持 4 不动——加深只是多吃内存。

### 各参数组合（128 MB，2 轮）

| 配置 | 吞吐 |
|------|------|
| 默认（MSS 1500 / window 10 MB） | 125 MB/s |
| MSS 8900 | 160 MB/s |
| MSS 8900 + window 128 MB | 181 MB/s |
| MSS 1500 + window 128 MB | 152 MB/s |
| `--no-cc` | **236 MB/s** |

`--no-cc` 在直连链路上提升最明显，但会失去对丢包的退让能力，共享链路不要用。

### 吞吐随文件大小变化（暴露固定开销）

同一套参数（MSS 8900 / window 128 MB）只改文件大小：

| 文件大小 | 吞吐 | 说明 |
|----------|------|------|
| 16 MB | 25 MB/s | 完全被固定开销吃掉 |
| 64 MB | 96 MB/s | 还在爬坡 |
| 256 MB | 388 MB/s | 接近稳态 |
| 512 MB | 568 MB/s | 稳态 |

反推固定开销约 **0.6 秒**。拆开看：UDT 握手 + 慢启动爬坡 + 缓冲预热。

进一步定位到慢启动：`CUDTCC::init()` 里 `m_dCWndSize = 16`（16 个包），
每次翻倍要等一个 `m_iRCInterval`（10 ms）。传大文件时这点时间可以忽略，
传几十 MB 就很明显了。

### `--fast-start` 的效果

新增的 `FastStartCC` 直接把初始窗口给到最大，跳过爬坡：

| 文件大小 | 默认 | `--fast-start` | 提升 |
|----------|------|-----------------|------|
| 16 MB | 25 MB/s | 116 MB/s | **4.6×** |
| 64 MB | 97 MB/s | 411 MB/s | **4.2×** |
| 512 MB | 564 MB/s | 598 MB/s | 1.06× |

大文件提升有限（本来爬坡占比就小），小文件是数量级的差别。

### 丢包环境（unshare + tc netem 实测）

这是最有价值的一组数据。64 MB 文件，在受控丢包环境下对比：

| 丢包率 | 默认 | `--fast-start` | 提升 |
|--------|------|-----------------|------|
| 0% | 96.5 MB/s | 400.4 MB/s | 4.1× |
| 1% | 11.0 MB/s | 129.5 MB/s | 11.8× |
| 2% | 6.8 MB/s | 127.9 MB/s | 18.8× |
| 5% | 2.4 MB/s | 59.7 MB/s | 24.9× |

**丢包越严重，差距越大**。原因：默认 CUDTCC 的 `onACK` 每 10 ms 才处理一次，
丢包让 ACK 变稀疏，拥塞窗口卡在 16 个包上不去（报告里 `window_cong: 16` 而
`window_flow: 15128`，一眼就能看出问题）。

`--fast-start` 绕过了这个爬坡逻辑，所以不受影响。

> **注意**：这不代表 `--fast-start` 适合公网。它不做拥塞退让，
> 在共享链路上会挤占别人带宽。它真正适合的场景是**链路质量差但可控**
> （比如自家两条线路之间的专线、卫星链路），默认模式在这种链路上会退化到
> 几 MB/s，完全没法用。

## 四、踩过的坑（留作记录）

### 1. 「自动 MSS」是个错误设计

我试过让发送端默认不设 MSS，指望 UDT 自己协商出最优值。结果更糟：

UDT 握手取**双方较小值**。发送端不设就是 1500，接收端给了 8900，
于是接收端的 FC 按 8900 算包数、发送端却按 1500 发包，窗口严重失配：

- 512 MB 从 370 MB/s 掉到 **9.2 MB/s**（30 倍劣化）
- `pkt_recv` 从 60677 变成 368773，暴露了问题

**教训**：MSS 必须两端显式给同一个值。这就是功能测试第 15 条存在的原因——
光看「传输成功、哈希正确」完全发现不了这种问题。

### 2. `perfmon(clear)` 的误解

我一度以为 `perfmon(..., true)` 会把统计清零导致报告错误。读了 UDT 源码
（`core.cpp` 的 `CUDT::sample`）才确认：`clear` 只清**区间计数器**
（`m_llTraceSent` 等），报告用的 `pktSentTotal` 这类累计量不受影响。

反过来，进度显示必须用 `clear=true`，否则 `m_LastSampleTime` 不前进，
算出来的「瞬时速率」会退化成平均值。

### 3. `/tmp` 是 tmpfs

早期基准测试全在 `/tmp` 跑，而它是 tmpfs（内存盘），写盘开销被严重低估，
差点误判「瓶颈在磁盘」。基准脚本现在默认把数据放真实磁盘，并支持
`BENCH_DIR` 指定位置。

### 4. 测量脚本本身会骗人

早期用 `bc` 算吞吐，遇到小数下溢时输出过 107158 MB/s 这种荒谬值——
实际是传输失败、耗时接近 0。现在基准脚本每轮都校验退出码、文件大小、哈希，
校验不过直接丢弃该轮。

### 5. loopback 的噪声有 ±13%

同一配置连跑 10 次，吞吐在 563 ~ 642 MB/s 之间跳（中位 603，标准差 36）。

**这意味着任何小于 13% 的改动都无法用 loopback 验证**。我一开始不知道，
拿几次「块大小 1MB 比 4MB 快」的结论去调参，其实全在噪声里。
后来所有性能结论都要求：要么差距远超 13%，要么换指标（比如 CPU 时间、
或者用 netem 造出真实丢包放大差异）。

### 6. gprof 会说谎

用 `-pg` 编出来的 profile 显示 BLAKE3 占接收端 66% CPU，看起来是头号瓶颈。
但总采样只有 0.21 秒，而实际传输跑了 0.9 秒——**多线程程序的 gprof 统计不全**。

验证方法：把 BLAKE3 整个换成空操作再测，吞吐只快 1.4%（574.6 vs 582.6），
远小于噪声。所以 BLAKE3 根本不是瓶颈，gprof 的结论是错的。

教训：profiler 的百分比要先确认采样覆盖完整，否则会把人带沟里。

### 7. 接收端的 retrans 恒为 0

UDT 的 `pktRetransTotal` 只统计**本端重传了多少包**。接收端不发送数据，
所以这个值永远是 0。原来的报告拿它算「重传率」，结论永远是「网络优秀」，
哪怕链路丢了 5% 的包。

现在报告里额外给 `recv_loss_ratio`（`pktRcvLossTotal / pktRecvTotal`），
并加了一行 `retrans_note` 说明口径。实测 5% netem 丢包下
`recv_loss_ratio = 4.32%`，诊断从「excellent」正确变成「network_lossy」。

## 五、没测到的部分

诚实说明，以下没有验证：

- **Windows 分支完全没测**（本机无 MinGW，无法交叉编译验证）
- **真实跨机网络**：丢包是用 netem 在本机模拟的，跟真实链路（乱序、突发丢包、
  带宽限制、NAT 超时）仍有差距
- **ARM 平台**（有预编译 blake3 库，但没实机跑）
- `--fast-start` / `--no-cc` 在共享链路上对其他流量的影响（这需要多机多流环境）
- 长时间稳定性（目前最长单次 512 MB，没有跑过小时级）
- 并发多连接（当前实现是单连接，传完即退出）
- 极端丢包（>10%）和完全断链恢复

如果要在生产环境用，建议至少补上真实网络测试和 Windows 测试。
